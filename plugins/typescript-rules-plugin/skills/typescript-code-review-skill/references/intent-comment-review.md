# コメント意図・防御的コードレビュープロンプト

目的: コメントがコードから読み取れない意図（Why-not / 局所的な Why）を運んでいるか、および仕様が要求しない「念のため」の防御的コード・フォールバックがないかをレビューする。

## レビューポリシー

### コメントの意図原則

将来のメンテナは、仕組みはコードで、契約はテストで、制約はコメントで探す。コメントはコードだけでは読み取れない制約を残す場所として使う。

- **Why-not** を書く: 却下した代替案、危険な単純化、過去の落とし穴、互換性制約、性能上の崖
- **局所的な Why** も書いてよい: 順序依存・セキュリティ境界など、その理由をコードのそばで読めないと将来の編集者が誤って壊しそうな場合
- コードの How を言い換えるだけのコメントは消す（コードだけが変更されると嘘になる）
- 出典がある制約は Issue 番号や仕様書番号を添える。ただし番号だけのコメントにはしない — 要点を一行で書いた上で番号を付ける

### 防御的コードの原則

仕様が要求していない「念のため」のフォールバックや防御的コードは原則禁止。不要な分岐はテストされない死んだ経路を増やし、実際の失敗を握りつぶす。

- エラー処理は仕様が要求する場所（システム境界、エントリポイント、ハンドラ）にだけ書き、それ以外では失敗をそのまま伝播させる
- フォールバックが本当に仕様（合意済みの劣化提供）なら3点セットを揃える: ①理由と出典を書いたコメント ②観測手段（ログ・メトリクス）③挙動を固定するテスト

## チェックリスト

### コメント

- [ ] How の言い換えコメント（コードを読めば分かる内容の繰り返し）がないか
- [ ] 「もっと単純にできそう」に見える箇所に、単純化しない理由（Why-not）が残っているか
- [ ] 順序依存・セキュリティ境界など、壊し方が非自明な箇所に局所的な Why が残っているか
- [ ] 番号だけのコメント（`// #482`）がないか — 要点一行+番号に置換
- [ ] コードの変更に追従せず嘘になっているコメントがないか

### 防御的コード

- [ ] 起こりえないエラーへの try-catch がないか
- [ ] 呼び出し元が処理すべき例外をその場で catch して null/既定値に変換していないか
- [ ] 型で保証済みの値への「とりあえず」の optional chaining・既定値（`?.` / `?? ""`）がないか
- [ ] 失敗時に黙って別実装・既定値へ切り替えるフォールバックがないか
- [ ] 仕様としてのフォールバックに3点セット（コメント+出典 / 観測手段 / テスト）が揃っているか

## 具体例

### How の言い換え — 削除

```typescript
// 悪い例
// ユーザーIDでキャッシュを検索する
const cached = cache.get(userId);

// ステータスが active か確認してからメールを送る
if (user.status === "active") {
  await sendMail(user);
}
```

コードを読めば分かることの繰り返し。条件が変わるたびにコメントの追従が必要になるだけで、情報を足していない。

### Why-not — 保持・推奨

```typescript
// 良い例（却下した代替案）
// Map ではなく LRU を使う。セッション数は無制限に増えるため、
// 素朴な Map に置き換えるとメモリリークが再発する（#482）。
const cached = lruCache.get(userId);

// 良い例（互換性制約）
// レスポンスの日付は ISO 8601 ではなく epoch 秒のまま返す。
// v1 クライアント（モバイルの旧バージョン）が数値前提でパースしており、
// 形式を変えると強制アップデートなしでは壊れる。
res.json({ createdAt: toEpochSeconds(order.createdAt) });
```

### 局所的な Why — 保持・推奨

```typescript
// 順序が重要: 監査ログは課金確定の前に書く。
// 逆にすると課金失敗時に監査証跡が残らない。
await auditLog.record(order);
await billing.charge(order);

// ファイル名はクライアント入力をそのまま使わず必ず再生成する。
// パストラバーサル（../）対策で、ここが唯一の防御点。
const safeName = generateFileName(upload.extension);
```

順序を入れ替えてもコンパイルは通り、テストもすり抜けやすい。壊れ方が非自明な箇所はその場に理由を残す。

### 出典番号の添え方

```typescript
// 悪い例: 番号だけ — 参照先が消えたり読めない環境では意図も消える
// #482
const cached = lruCache.get(userId);

// 良い例: 要点を一行で書いた上で番号を付ける
// 素朴な Map だとセッション増でメモリリークする（#482）。
const cached = lruCache.get(userId);
```

### 不要な try-catch — 削除

```typescript
// 悪い例
function getUser(id: string): User | null {
  try {
    return repo.findById(id);
  } catch {
    return null;
  }
}

// 良い例: 失敗をそのまま伝播させる
function getUser(id: string): User | null {
  return repo.findById(id);
}
```

`findById` は見つからなければ null を返す設計で、ここで捕まえるべき例外はない。「念のため」の catch は DB 接続断などの本来伝播すべき失敗まで null に変換し、呼び出し元で「ユーザーがいない」と区別できなくなる。

### とりあえずの既定値 — 削除

```typescript
// 悪い例: 型定義上 profile は必須フィールド
const name = user.profile?.name ?? "";
```

型で保証済みの値への「とりあえず」の防御。本当に欠けるならデータ不整合であり、空文字でごまかさず失敗させるべき。

### 仕様としてのフォールバック — 3点セットを確認

```typescript
try {
  return await recommendItems(userId, limit);
} catch (err) {
  // 推薦APIの障害時は人気順で代替する（SPEC-044）。
  // 推薦は補助機能であり、一覧ごと落とすより劣化提供が望ましいと合意済み。
  // 障害に気づけるよう warn ログとメトリクスを必ず残す。
  logger.warn("recommendation fallback", { err });
  metrics.increment("recommend.fallback");
  return popularItems(limit);
}
```

Why と出典のコメント、観測手段（ログ・メトリクス）が揃っている。このフォールバック挙動自体をテストで固定されているかも確認する。

## 重要度分類

### 🔴 Blocking

- 例外の握りつぶし（catch して null/既定値で続行し、実際の失敗を隠すもの）
- 失敗時に黙って別実装へ切り替える、仕様にないフォールバック
- 実装と矛盾して嘘になっているコメント

### 🟡 Should Fix

- 型で保証済みの値への「とりあえず」の防御・既定値
- 起こりえないエラーへの try-catch
- 仕様フォールバックの3点セット不足（コメント・観測手段・テストのいずれか欠落）
- How の言い換えコメント
- 番号だけのコメント（要点一行+番号に置換）

### 🟢 Nice to Have

- 「単純化できそう」に見える箇所への Why-not コメントの追加提案
- 順序依存・セキュリティ境界への局所的な Why の追加提案
- エラー処理のシステム境界への集約

## 特記事項

- Why-not / 局所的な Why のコメントは削除提案しない — 削除は読み手から制約情報を奪う
- 「エラーハンドリングが冗長」に見えても、仕様（要件・エッジケース網羅）が要求している場合は防御的コードではない。仕様の裏付けを確認してから指摘する
